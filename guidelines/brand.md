# ブランドらしさ

wip-ui のコンポーネントと、それを使った UI を、ロリポップのブランドらしく作るための判断の基準です。
コンポーネントを作る・直すときに読みます。
他のブランドの場合の基準や画面を組むときの基準は、あとで足します。

元になっているのは Brand Identity（BI）と Visual Identity（VI）です。食い違う場合は BI・VI を正とします。

- BI: https://app.notion.com/p/pepabo/Brand-Identity-34371085cfd98014af1ae00218cb6c67
- VI: https://app.notion.com/p/pepabo/Visual-Identity-34371085cfd980ff8a25eb895fef630d

BI にある 4 つの価値を、コンポーネントの観点で言葉にしたものが「軸」です。ルールは、軸を元に書いています。
ルールにない判断は、軸に戻って決めます。

## 軸

### 1. 日本一親しみやすく簡単なホスティングサービスを提供する

ユーザーは、裏側の仕組みを知らなくても、迷わずやりたいことを終えたい。
簡単で親しみやすく見えるが、チープには見えない。

### 2. 表現しやすいように整備された基盤を提供する

ユーザーは、決まったやり方の上で、自分のやりたいことに集中したい。
決まっているが、窮屈ではない。

### 3. インフラを任せることができ、事業に集中できる

ユーザーは、裏側を見張らずに、任せきりにしたい。
頼れるが、馴れ馴れしくはない。

### 4. レガシーさを感じさせることなく常に新しい物を取り入れる

ユーザーは、ちゃんと手入れされているサービスを使っている、と感じたい。
新しいが、モダンさを見せることが目的ではない。

## コンポーネントを作るとき

ルールどうしがぶつかったら、「伝え方」と「安全」を「作り」と「見た目」より優先します。BI のミッションが「安全とわかりやすさでユーザーの創造性を支える」だからです。

### 作り

- 要素や prop を持たせるかは、それがないと用途を果たせないかで決める。果たせるなら持たせない。カスタマイズの幅が広がるほど、画面ごとに体験がばらつく
- 既定値は、標準の使い方にする。props を渡さなくても、そのまま一貫した見た目と動きになるようにする
- 1 つのコンポーネントは、1 つの用途だけを持つ。何にでも使えるコンポーネントは作らない
- それぞれの UI コンポーネントには、世間で定着した用途と振る舞いがある（Switch は切り替えるとすぐ反映される、Tab は同じ画面の中で表示を切り替える、など）。そこから大きく外れた使い方や動きを提供しない。知っている動きと違うと、ユーザーに学習コストがかかる
- 見た目に関わる props（余白、色、大きさなど）の値は、意味の付いた決まった段階（余白なら xs〜xxxl、色なら negative のような用途の名前）から選ばせる。任意の px や色コードは受け付けない
- 使う側が HTML や CSS を足さなくても正しくなる、完成した形で提供する

### 伝え方

- 色と動きは、意味の付いたもの（意味色、状態のトークン）だけを使う。同じ意味には、常に同じ色と動きを当てる
- 処理中、完了、失敗などの状態を表せる形を持つ。操作の対象と今の状態が、ユーザーが確かめに行かなくてもひと目で分かるように見せる
- 平常時は、基調の色だけで描き、強い色、動き、強調を出さない。失敗や警告など、ユーザーの対応が要るときだけ、意味色やアイコンではっきり目立たせる
- 成功を演出で飾らず、失敗をぼかさない
- 異常や警告を示すコンポーネントは、何が起きたかの文だけでなく、ユーザーが次に何をすればよいか（説明やボタン）を置ける形にする

### 安全

- パスワードや API キーなど、見られて困る値を扱う場面があるなら、伏せた状態で表示し、ユーザーの操作で見せられる手段（コンポーネントや prop）を提供する
- 操作の結果がユーザーの予想と違うもの（新しいタブが開く、外のサイトへ出る、ファイルがダウンロードされる、など）は、操作の前にそうと分かる印を、コンポーネントが自動で付ける

### 見た目

- フラットを原則にする。影や厚みは、状態を示すとき（浮いている Dialog など）と、全体のトーンに合う範囲でだけ使う
- 親しみやすさ、とっつきやすさは、丸みとやわらかさで出す
- 操作できるコンポーネントは、押しやすい大きさと余白を取る。文字も含め、サイズの段階のうち最小のものを既定にしない
- 余白と高いコントラストで見せる。詰め込まない
